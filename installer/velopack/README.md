# Experimental Velopack recovery patch

This is an **unverified candidate**, not an approved updater. Source is Velopack 1.2.161, commit `92d6a1c91716729d449034df5c50307dcce39493`, under the accompanying MIT license. The patch makes timeout or unconfirmed process waits fail, refuses to replace while another identifiable package process is running, keeps the previous payload at `tempo-previous`, and attempts restoration if activation rename fails. `tempo-update-pending.txt` persists until an independently designed confirmation or repair process resolves it. No cleanup or confirmation mechanism has been approved here.

Windows process enumeration may fail to inspect inaccessible processes; this patch does not prove all processes have exited. The coordinator must enforce the separate cross-instance lock and actual process-exit requirement. Examine the wait APIs' already-exited behavior and updater elevation/restart interactions on Windows. Patch review and native tests are mandatory before any use.

To prepare an isolated clean upstream checkout, run `python scripts/prepare_velopack_updater.py <checkout>`. The command checks the commit, cleanliness, patch digest and each changed upstream file before applying. Build with `cargo build --locked --release -p velopack_bins --bin update --features windows --target x86_64-pc-windows-msvc` in that checkout. The manual Windows workflow builds a separate fixture-only binary, installs real disposable PyInstaller packages, and runs failure scenarios. It reports actual outcomes, but the recovery gate remains closed until independent repair, health confirmation, and successive-update scenarios exist and pass. The workflow does not publish unverified binaries.

The fixture uses two minimal Windows packages with Velopack lifecycle startup and a distinct compile-time fault-injection build. Before opening the gate, add and run remaining scenarios: locked files, failed restart, installation repair without the GUI, confirmation, and two subsequent updates. Check both retained bytes and actual launchability, old/new data compatibility, transaction markers, shortcuts, and component selection. Confirm a verified known-good installer is available offline outside updater-managed directories. The workflow must fail if any fixture or scenario is missing; compile success is not recovery acceptance.
